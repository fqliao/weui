# 自定义网站登录问题排查与修复

日期：2026-09-14。当前测试浏览器固定为 Google Chrome，UI 操作继续使用 Midscene。

## 实际发现

1. 原运行 `e5f2a82b-4324-4d1a-94a9-a196e34ea61a` 在浏览器启动阶段失败：动作 0、视觉调用 0，尚未访问网站或执行登录。当时没有记录更细的操作系统退出原因；之后同一 Edge 版本单独启动成功，未稳定复现，不能据此判断账号有错。
2. 再次诊断看到页面仍显示 `Logging in...`，执行器已经检查登录成功条件。已在提交后增加 Midscene 条件等待，再进行最终断言。
3. Chrome 重跑 `95e44ee7-a447-413f-8fe9-e8f7f861a075` 已经成功登录并进入 Dashboard；原用例又要求输入账号密码并点击 Login，因此找不到登录表单，结果为 INCONCLUSIVE。
4. 原用例把成功登录与错误账号登录提示放在同一组最终预期中。框架在步骤完成后的同一个页面检查所有预期，因此这两个场景需要分别执行。

网站地址 `/#/auth/login` 与原登录配置 `/login` 均可打开登录页面，本次没有把路径差异判为阻断原因。

## 已修复的平台行为

- 本机 `.env` 固定 `BROWSER_EXECUTABLE_PATH=C:/Program Files/Google/Chrome/Application/chrome.exe`。自动发现不再选择 Edge，当前实测版本为 Chrome 152.0.7977.83。
- 浏览器启动最多尝试两次；该重试发生在访问网站之前，不重放登录或业务动作。
- 运行时间线记录启动次数、路径、失败详情和实际浏览器版本。无效的显式路径直接报错，不静默切换浏览器。
- 连续启动失败有明确的 `BROWSER_LAUNCH_FAILED` 错误码。取消期间启动成功的浏览器会关闭。
- 登录提交后等待配置的可见成功条件，再断言；常规业务步骤仍在登录成功后执行。
- 新增 `pnpm browser:check` 检查浏览器启动、独立会话和截图；`pnpm health` 检查应用及基础服务。
