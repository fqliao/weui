# UI Agent 知识库组织与治理方案

版本：v1.1 | 日期：2026-09-13。本文同时收录于总方案 v1.4 第 17 节。以下是已确定的建设路线与待实现设计，未创建运行中的企业知识库，示例不代表真实业务规则。

## 17 知识库：LLM Wiki、轻量领域本体与独立断言

### 建设结论与职责

采用 **LLM Wiki + 轻量领域本体 + 独立断言**。LLM Wiki 负责整理与维护可阅读的知识；本体统一概念、稳定标识和关系；版本化规则与程序断言提供测试依据。首期用 Markdown、YAML/JSON、Git 和结构化查询形成闭环，向量数据库、完整 OWL 推理栈及图数据库不作为首期前提。

LLM Wiki 是知识管理模式：保留原始资料，持续生成关联页面，并维护索引、来源和变更记录。Karpathy 原文描述的是模式而非产品，本项目在此基础上增加审核、版本和权限设计，不采用模型对正式知识无限制改写的方式。[LLM Wiki 原始方案](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

本体建模、Wiki 与检索承担不同职责。Wiki 双链需配合明确的概念类型与关系校验，才可支持精确的依赖查询；本体也不能自行保证场景覆盖。RAG 可以使用文件、数据库或图查询，不仅限于向量检索；Wiki 增长后可增加关键词或语义检索，并用实际任务验证收益。[LangChain 检索说明](https://docs.langchain.com/oss/javascript/deepagents/retrieval)

### 知识分层与首期存储

以下目录是建议布局，名称均为仓库相对路径。原始资料、规则、本体与测试资产各有唯一维护位置；Wiki 引用这些内容，不另存一份可独立修改的验收标准。

| 层次 / 位置 | 内容与权威范围 | 首期维护方式 |
| --- | --- | --- |
| 原始资料：knowledge/raw | 需求、契约、制度、缺陷记录的版本快照；为结论提供来源 | 保存来源 ID、版本、定位与摘要哈希；新版本追加，保留旧记录。大文件与敏感附件使用受控存储引用 |
| 领域 Wiki：knowledge/wiki | 对象、角色、流程、测试方法、经验与来源解释 | Markdown 页面、index、追加式 log；由 LLM 生成草稿，经校验和评审发布 |
| 轻量本体：knowledge/ontology | 概念类型、稳定 ID、类型化关系与允许的字段 | YAML/JSON 描述，schema 与引用完整性校验；维护者审核模型结构变更 |
| 正式业务规则：knowledge/rules | 适用条件、预期、不变量、优先级、来源与有效版本 | 业务/QA 确认，作为断言依据；与 Wiki 冲突时停止并处理冲突 |
| 执行资产：cases、tests、fixtures | 用例、可执行断言、数据准备与清理适配器 | 测试开发维护；关联规则 ID 和版本，代码评审与反例验证 |
| 发布与评测：knowledge/releases、evals/knowledge | 发布清单、兼容版本、查询与变更反例集 | 发布快照不可变；记录审核、依赖和回滚目标 |

现有 specs 用于需求入口与原文引用，已确认的可执行验收规则统一归入 knowledge/rules，避免 specs 与规则库同时成为可写的正确答案。Wiki 中的概括、模型推断和未解决问题分别标注，不把推断自动升级为业务规则。

### 业务本体与测试本体的连接

首期围绕申请审批建模，再将验证过的公共概念扩展到另外两条链路。

| 概念范围 | 代表概念 | 代表关系 |
| --- | --- | --- |
| 业务领域 | 业务对象、角色、流程、状态、动作 | 角色执行动作；动作作用于对象；动作具有前置状态和后置状态 |
| 规则与来源 | 业务规则、需求条款、接口契约、版本 | 规则约束动作；规则来源于条款；新规则替代指定旧版本 |
| 测试领域 | 风险、场景、用例、断言、数据工厂 | 用例覆盖规则；断言验证预期；用例依赖数据工厂 |
| 执行与证据 | 页面组件、业务 API、运行、证据 | 业务动作映射工具；运行执行用例；证据支持某次断言 |

关系名、两端允许的类型和基数由 schema 明确定义。规则到用例的覆盖关系可用于查漏；运行记录另存实际 PASS/FAIL/BLOCKED 等状态，不能用“有一个用例链接”代替有效覆盖或通过结论。状态迁移、组合与边界覆盖需要独立的覆盖策略。

本体采用开放语义时，缺少某事实不能直接推断为假。若后续采用 RDF/OWL，SHACL 可校验图结构和显式条件；时序、业务写入与权限结果仍由专门的规则和程序断言验证。[OWL 语义](https://www.w3.org/TR/owl2-primer/)、[SHACL](https://www.w3.org/TR/shacl/)

### 页面、规则与发布清单的契约

每张知识页面至少记录稳定 ID、类型、业务域、适用应用版本、来源定位、关系、负责人、审核状态、更新时间与替代关系。来源定位应能落到需求条款、文档页码或代码提交，不能只链接到一个大型目录。资料密级与项目权限随页面和索引传播。

示例为平台自定义元数据草案，不是 Deep Agents 的内置 schema；下列编号均为演示数据。

```yaml
id: WIKI-APPROVAL-SELF
type: test_scenario
domain: approval
status: draft
owner: pilot_qa_owner
source_refs: [DEMO-SPEC-01@v1#section-3]
rule_refs: [DEMO-RULE-SELF@v1]
relations:
  covers: [DEMO-RISK-SELF]
  uses_case: [DEMO-CASE-SELF]
unresolved_questions: []
```

发布清单固定 knowledge_release_id、原始来源版本、Wiki/本体/规则哈希、审核记录、兼容应用版本及用例/断言制品引用。发布前验证所有依赖可解析；运行时再与实际测试制品匹配。目录别名可以指向最新版本，但任务开始后必须解析为不可变的具体版本。

### 编写、发布与运行分离

知识维护流程：收录原始资料快照 → LLM 生成页面和关系变更草稿 → 程序 lint → 业务/QA 复核规则与冲突 → 发布不可变快照 → 标记受影响用例 → 对受影响资产重新验证。

程序 lint 检查字段、来源、断链、重复 ID、状态和版本匹配；LLM 辅助发现表述矛盾，但不能独自证明知识真实。来源变更通过反向引用标记关联页面和用例待复核，不能只更新概要而保留过期预期。多位作者通过分支和差异合并协作，发布使用一致的快照清单，避免读取半更新目录。

运行任务只能读取已授权且已发布的快照；知识维护身份只能写候选区，不能凭模型输出发布规则。发布服务依据评审记录完成晋级。新发现以候选形式回流，不改变当前任务的验收条件。需要例外规则时先完成规则确认并创建新的计划或任务版本。

查询先按项目、业务域、权限、应用版本和知识版本过滤，再读取页面或扩展关系。共享索引、摘要和工具返回值同样执行过滤。涉及敏感原文时只返回授权片段或证据引用，凭证保存在企业凭证服务中。原文中的指令作为资料内容，不授予新的工具权限。

### Deep Agents 如何访问知识

Skills 描述“如何查知识、如何设计场景、如何引用证据”；业务规则留在规则库。知识库通过文件或自定义工具按需读取，避免将全部知识塞入系统提示词。任务的知识版本与关键规则 ID 独立保存，不能仅依靠上下文摘要。[Deep Agents Skills](https://docs.langchain.com/oss/javascript/deepagents/skills)

| 拟建接口 | 输入与返回 | 运行约束 |
| --- | --- | --- |
| knowledge.search | 查询文本、业务域、release_id；返回命中页面、版本与来源 | 先过滤授权范围；返回限量摘要和引用 |
| knowledge.get_rule | 规则 ID、release_id；返回适用条件、固定预期、来源与审核状态 | 校验正式状态及应用版本，不回退到任意相似规则 |
| knowledge.get_flow | 流程 ID、release_id；返回状态、动作、角色与关联规则 | 按关系类型扩展，并限制深度与数量 |
| knowledge.get_impact | 变更 ID、基准/目标版本；返回关联页面、用例与断言 | 基于已登记依赖计算影响，披露未知和未建模依赖 |

上述为本平台待开发工具，不是框架默认能力。接口统一纳入第 18 节工具目录与权限校验。关键规则缺失、冲突、失效或版本不匹配时，该用例记为知识前置条件阻断；业务证据不足按结果规范记为不确定。不能使用当前页面行为猜测“正确答案”。

### 一次审批测试如何使用

用户输入“验证申请人不能审批自己”，平台锁定知识版本和测试角色。Agent 读取流程、规则与历史用例，输出关联规则 ID 的候选计划；覆盖策略检查正常审批、自审批、无权角色和非法状态等适用场景。

执行器使用本次任务的数据，经 UI 尝试自审批；独立断言按已确认规则检查请求是否被拒绝、业务状态是否未改变以及是否没有产生成功审批记录。报告同时保留规则来源、知识版本、实际证据和结果，避免只看拒绝提示。若产生“拒绝事件是否也必须审计”的新问题，应登记为待确认事项，不临时补写规则。

业务规则发生变化时，知识维护流程提交新草稿并给出受影响用例清单；旧运行继续引用旧快照，新运行使用经过评审的新快照。确认后的测试经验可以进入 Wiki，但不能用失败结果自动覆盖验收依据。

### 试点验收与后续扩展

MVP 第 1-6 周交付一条链路的最小知识快照、授权查询和 Web 阅读/规则引用，对应开发清单 M10/M20/M25；资料整理和发布可由维护者通过版本化导入完成，普通测试人员的使用流程全部在 Web。v0.2 的 K01/K02 补齐 Web 编辑、LLM 摄取草稿、评审发布、回滚与变更影响；E05 完成本体与覆盖可视化。以下检查按对应能力进入的版本验收，资源以《MVP开发任务清单与迭代路线》为准。

| 检查项 | 验证方式与首期要求 |
| --- | --- |
| 来源可追溯 | 范围内关键规则均有可定位来源、负责人和评审记录；每次运行记录知识版本 |
| 查询与覆盖 | 用人工标注的代表任务检查规则命中、版本选择、来源准确性和覆盖缺口，披露漏检与误检 |
| 变更影响 | 注入规则替代、删除、断链和跨页面冲突；相关资产进入复核，不能静默沿用旧规则 |
| 运行隔离 | 反例集中草稿、错误版本及无权知识均不能进入正式任务，历史任务快照可重现 |
| 判定独立 | 真实失败不触发自动放宽规则；缺失关键依据可明确阻断并给出原因 |
| 维护收益 | 对照直接阅读原文的同类任务，统计编写、审核、查询、修订总工时及模型费用，不预填节省比例 |

知识评测集单独标记，不能混入业务测试成功率的分母。首期记录查询基线；覆盖依赖未建模完整时，影响清单不能宣称穷尽。Wiki 更新、人工校核和重建索引的成本计入总成本。

当目录索引和关键词检索出现持续漏检或延迟超标，再对同一评测集比较全文与语义检索；当类型化关系查询成为主要瓶颈，再比较关系库与图存储；存在明确的形式化推理需求时，再评估 OWL/规则引擎。采用任何扩展都保留来源、权限和版本契约。
