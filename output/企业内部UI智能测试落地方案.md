## 01 决策摘要：先建立可信回归，再引入有边界的探索

建议建立两条相互衔接的流程：**稳定回归验证已知业务规则，Agent 探索发现遗漏场景并生成候选资产**。两者共享业务知识、数据准备、执行工具和证据存储，但采用不同的准入标准。

稳定回归以版本化、可重复执行的测试代码为主要资产；关键业务断言由规则和程序判定。Agent 用于需求拆解、候选用例生成、异常与边界探索、失败分析及修复建议。探索发现经过复现、评审和稳定性观察后，进入回归库。

这一架构是本文对 A1 的工程能力建设、A2 的探索与资产沉淀、A3 的分层质量体系、A4 的业务结果验证的综合建议，并非某份演讲给出的统一标准。

| 首期决策 | 建议 | 交付结果 |
| --- | --- | --- |
| 试点对象 | MVP 为 1 个内部 Web 系统、1 条业务链路；后续扩至 3 条 | 明确需求、权限、数据和成功条件 |
| 回归底座 | 核心采用 TypeScript + Playwright；成熟存量资产可经工具复用 | 可在 CI 运行的稳定用例与报告 |
| 视觉执行 | 重点试点 Midscene SDK，与 Playwright 混合使用 | 视觉操作、辅助断言及探索的对照数据，详见第 15 节 |
| Agent 开发框架 | 采用 Deep Agents TS（基于 LangGraph）；有明确障碍才启动框架对照 | 知识、上下文、任务运行与受限执行接口，详见第 16 节 |

## 02 四份资料分别贡献了什么

已检查 reference 目录下全部 122 页：A1 38 页、A2 27 页、A3 28 页、A4 29 页。A1、A3、A4 大量正文嵌在图片中，因此结合页面渲染与文本抽取阅读。下文页码均指 PDF 物理页，从 1 开始；各文件末尾的会议宣传页未作为技术依据。

### A1：工程能力决定能否规模化

《大脑不够，还要手脚：智能测试规模化落地的工程真相》覆盖 GUI、服务端、压测和研发流程。p.9-12 用“场景 × 操作”的能力矩阵定位无法自动化的原因；p.14-15 展示配置、登录、工具调用、执行、验证与清理的完整链路；p.18-21 将配置、账号、数据查询和消息验证封装成可复用能力；p.27-32 讨论把这些能力接入研发流程。

**内部转化：**先盘点账号、权限、测试数据、第三方依赖、环境配置和结果查询缺口，再按阻塞频率补齐。把“创建申请”“准备审批人”“查询审计事件”等能力封装成受限接口，而不是让模型任意操作数据库。

**适用边界：**移动端 ADB、设备机架不直接适用于 Web；“QA 只负责资金”等组织安排属于其试点选择，不能照搬。p.10 的“70%”是该案例能力矩阵中不可转化类别的占比，不是 Agent 执行成功率；p.29 的指标也有各自分母，不能混成一个自动化率。

### A2：探索要有覆盖策略、收敛机制和可回放产物

《基于多模态 Agent 的 UI 自动化路径智能规划》围绕营销配置场景。p.8-11 强调专用探索流程、当前页面状态和标准用例产物；p.14-17 分别处理感知、指令可执行性、循环探索和执行中断；p.19 指出只调 prompt、让模型自行决定停止、只看跑通而忽略断言等问题；p.20 的需求测新和缺陷模式迁移属于后续规划。

**内部转化：**按“主链路 → 边界 → 其他路径”分阶段探索；每次操作前后观察状态；对动作类型、元素唯一性和资源预算进行程序校验；产物必须包含业务预期、断言、数据准备和清理。

**适用边界：**p.4 的“10 条/天”“边界不足 30%”是案例背景，不是引入 Agent 后的提升结果。DOM 可以提供 disabled、aria-disabled 等状态，不能把演讲中的视觉/DOM 对比理解为 DOM 完全不能识别置灰。Agent 同样可能带有先验偏差，不能因为“自主探索”就假定覆盖完整。

### A3：既要测试业务，也要评测测试智能体

《腾讯 Marvis 质量保障实战》主要讨论操作系统级 AI 办公智能体本身的质量。p.9-12 展示分层测试、BDD/TDD 与跨角色协作；p.14-17 展示知识库、E2E 架构和执行基础设施；p.18-19 分离评测集、适配器、评测器、任务与报告；p.21 区分基础质量、模型质量和专项质量。

**内部转化：**业务系统继续采用分层测试；同时为测试 Agent 建立独立评测集，评估误通过、漏检、执行完成率、耗时和成本。需求与验收条件前置，不能等测试生成后再由同一个模型补写“正确答案”。

**适用边界：**“用 AI 测 Web 系统”和“测试 AI 产品”是两个对象。若内部产品没有 AI 功能，不必引入办公智能体的文件生成、内容满意度等评测；但测试 Agent 自身的结果判定仍需评测。

### A4：动作成功必须进一步验证业务目标

《基于业务链路的 Web UI Agent 智能化测试实践》与内部 Web 场景最贴近。p.9-11 展示任务接入、调度、编排、执行、结果和运行护栏；p.14 主张结构化短计划和短循环，关键状态变化后再规划；p.16 用 DOM/ARIA 缩小候选，必要时通过带编号截图辅助选择；p.18-20 以动作前后证据、分层裁决和任务验收形成可信结论。

**内部转化：**把目标拆成可验收的业务状态；先用语义定位，再对歧义目标补充视觉证据；每步验证对象与效果；最终核对原始验收条件。报告保留通过、失败和不确定，独立标注访问阻断与环境异常。

**适用边界：**该分享对写操作采用提议与确认的保守设置；内部隔离测试环境可通过预授权策略运行明确范围内的写操作，前提是执行层约束租户、账号、对象和动作。会议中的未来规划不等于已实现能力。

### 试点优先选择什么

首选数据可重置、预期明确、人工重复回归较多的流程。MVP 先选一条链路，后续可扩展的三条示例链路为：登录与角色菜单；申请创建、提交与审批；查询、筛选与导出。这些是通用示例，不代表已确认企业实际模块。

每条链路按 1-5 分评价业务风险、回归频次、历史缺陷和维护痛点，再确认环境与数据是否具备。可用“风险 × 35% + 频次 × 25% + 缺陷 × 20% + 痛点 × 20%”排序，权重由试点负责人确认。环境不可隔离、无正确性判断依据的链路，即使评分高，也先作为基础能力建设项目。

| 情况 | 适合的首期方式 |
| --- | --- |
| 主流程稳定、结果明确 | 确定性 UI 回归 |
| 表单复杂、规则清楚、边界容易遗漏 | Agent 辅助设计与受限探索 |
| UI 经常调整，但控件语义稳定 | 语义定位、组件对象和修复建议 |
| 金额计算、权限、状态机大量组合 | 单元/API 层覆盖组合；UI 保留代表链路 |
| Canvas、复杂拖拽或纯视觉目标 | 小样本验证视觉方案，独立评估成本 |
| 真实付款、对外通知、生产数据删除 | 使用隔离替身与模拟账户；首期不在真实生产执行 |

## 04 测试分层与业务覆盖模型

UI 自动化承担用户视角的链路验证。计算规则、接口契约、权限和状态机应尽量在更快、诊断更明确的层级验证；不要把每个组合都扩展为长 UI 链路。这与 Google 对过度依赖 E2E 的讨论及 A3 p.9 的分层思路一致，不需要照搬固定的用例数量比例。[Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)

| 层级 | 重点验证 | 主要责任 |
| --- | --- | --- |
| 单元与组件 | 校验函数、金额精度、状态转换、控件交互 | 开发维护，QA 提供业务反例 |
| API 与集成 | 权限、跨租户隔离、幂等、数据一致性、服务协作 | 开发与测试开发共同维护 |
| 确定性 UI | 核心端到端链路、角色交接、页面反馈和持久化结果 | 业务 QA 定义预期，研发/测开实现 |
| Agent 探索 | 未覆盖边界、异常状态、变更页面的候选路径 | QA 设定范围和规则，复核发现 |
| 人工专项 | 易用性、复杂视觉体验、需求歧义和高风险判断 | 业务 QA、产品与领域专家 |

首期为每条链路建立“角色 × 业务状态 × 数据条件 × 操作 × 预期”的覆盖表。先确定风险点分母，再选择代表用例，不能用访问过多少页面替代覆盖率。

例如申请流程至少考虑：申请人/审批人/无权限用户，草稿/待审批/通过/驳回，合法/空值/越界/重复数据，以及提交、审批、重复提交、撤回等操作。只对有效或明确要求拒绝的组合生成用例，避免机械展开全部笛卡尔积。

MVP 先以一条链路的 12 条代表用例验收；v0.3 再扩展到三条链路和约 20-30 条维护资产。其中应主动纳入异常、边界和权限场景，具体数量由覆盖表决定。参数化变体可以增加测试点，但不重复计为新业务风险。

视觉和无障碍检查作为补充：视觉基线固定字体、操作系统、浏览器与动态区域处理方式，变更由人工审核；自动无障碍扫描不能替代键盘导航与辅助技术体验检查。[Playwright Visual comparisons](https://playwright.dev/docs/test-snapshots)、[Accessibility testing](https://playwright.dev/docs/accessibility-testing)

## 05 建议架构与技术选型

### 最小可行架构

需求/缺陷/业务规则 → 测试设计与风险表 → 两条执行流程 → 统一证据与结果 → 人工复核与资产更新。

**流程 A：**已审核用例 → 数据与账号准备 → 确定性执行 → 业务断言 → CI 门禁。

**流程 B：**探索目标 → 锁定知识与 Skill/工具版本 → 按需查知识 → 观察与规划 → 动作校验 → 受限执行 → 证据与候选发现 → 复现评审 → 流程 A 的资产库。

共享能力包括：身份与数据适配器、环境健康检查、浏览器驱动、动作策略、证据存储、版本记录、结果规范和指标。执行权限由工具层和环境层约束，提示词表达意图，但不充当权限边界。

| 能力 | 首期实现 | 何时再扩展 |
| --- | --- | --- |
| 用例与规则管理 | Git 中的 Markdown、YAML、测试代码 | 多业务线协作时对接用例平台 |
| 编排 | Deep Agents TS + 独立 Worker；任务、事件落 PostgreSQL，BullMQ/Redis 排队 | MVP 先保证取消、去重与故障终态，后续增加检查点安全恢复和 CI |
| 浏览器执行 | Playwright Test + 重点试点的 Midscene SDK；成熟存量框架可保留 | 按实际终端范围增加适配器 |
| AI 辅助 | 使用已有获准模型；固定提示词与输出格式 | 同一内部评测集验证后更换或分级路由 |
| 知识组织与访问 | LLM Wiki + 轻量本体；按业务域、权限和版本查询正式快照 | 语义检索或图存储按实际瓶颈扩展，详见第 17 节 |
| Skill 与工具 | Web 文本 Skill 模板/编辑/调试/发布；SDK 与业务 HTTP 适配器 | v0.2 扩展 MCP、自助接入和治理，再建设受控脚本运行器 |
| Web 与报告 | Next.js 工作台 + Fastify API；结构化结果、来源与证据页 | 第一版即有创建、计划确认、进度、报告、历史与反馈；后续扩展团队看板 |

### 工具选择依据

新建 Web 试点可优先验证 Playwright Test：语义定位、自动等待、隔离上下文和执行诊断适合本方案的回归底座。选择成立的前提是团队能维护相应代码与运行环境；不是对所有技术栈的普遍结论。[Playwright Best Practices](https://playwright.dev/docs/best-practices)

已有稳定 Selenium 资产可通过页面/组件对象改善维护性，先增加业务规则和结果规范，避免整体重写。页面对象负责页面操作，业务预期保留在测试层；必要的页面就绪校验可在对象中完成。[Selenium Page object models](https://www.selenium.dev/documentation/test_practices/encouraged/page_object_models/)

| 候选 | 可验证的能力 | 本方案位置 |
| --- | --- | --- |
| Playwright Test Agents | 官方提供 planner、generator、healer | 作为设计、生成、修复工作流的试点工具，输出仍须审核 |
| Playwright MCP | 向模型提供浏览器交互工具 | 工具接入选择之一，不等于完整测试平台 |
| Midscene | 视觉操作、自然语言任务、页面信息提取与断言；可集成 Playwright | 列为重点试点，比较普通表单、复杂视觉控件与有限探索；详见第 15 节 |

来源：[Playwright Test Agents](https://playwright.dev/docs/test-agents)、[Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp)、[Midscene 官方文档](https://midscenejs.com/)。

注意官方 healer 的结果可能包含 skipped test。因此，在内部发布流程中，healer 不能自动删除或跳过关键测试，不能修改业务预期来取得通过，也不能直接合并修复。工具升级需同步复查定义、固定依赖版本并运行内部基准集；不在本文承诺某个模型或工具的胜率。

Playwright MCP 官方也明确说明其不是安全边界，origin 配置不能替代网络隔离，且存在重定向边界。因此域名限制还需在执行器、代理或网络出口落实，不能仅配置 MCP 参数就认为环境已隔离。[Microsoft Playwright MCP 安全说明](https://github.com/microsoft/playwright-mcp#security)

平台层的推荐组合是 Deep Agents（基于 LangGraph）+ Playwright Test + Midscene SDK。Deep Agents 负责知识、上下文、任务拆解与分析生成，LangGraph 提供底层状态与运行能力，执行适配器管理浏览器和业务工具，独立判定器产出测试结论。已有 CI 回归可以直接运行，无需每条确定性用例都经过 Agent。选择依据、语言分支及恢复设计见第 16 节。

知识维护与任务执行使用分开的发布和权限路径：来源快照 → Wiki/本体/规则草稿 → 校验评审 → 知识发布；测试人员通过 Skill 模板编写方法，选择已注册工具并完成调试发布。任务服务解析已发布的知识、Skill、工具和断言版本；受控入口校验每次调用。运行中发现只能回流到候选区，不能直接改变正式规则和当前预期。

## 06 把业务目标变成有正确答案的用例

每个用例至少记录：稳定 ID、需求与规则版本、负责人、角色、前置状态、数据准备、执行目标、断言、风险等级、清理方法、执行环境及证据要求。步骤和预期分开存储，便于识别“换路径”和“改正确答案”的区别。运行清单额外锁定 knowledge_release_id、所用 Skill/工具版本和制品哈希；Wiki 说明引用正式规则，不成为另一份可独立修改的验收标准。

### 示例：双人审批

以下是自拟规则，只展示写法：申请人创建申请，审批人提交审批；申请人不得审批本人申请；审批完成后状态与审计记录应一致。具体角色和状态枚举需替换为企业规则。

| 阶段 | 动作 | 必须验证的事实 |
| --- | --- | --- |
| 准备 | 为本次运行创建独立申请人、审批人和数据 | 同一测试租户；角色与数据状态正确 |
| 创建 | 申请人在页面填写并提交 | 返回本次申请 ID；详情页显示待审批 |
| 审批 | 独立浏览器上下文登录审批人并审批 | 操作对象为该申请 ID；状态变为已通过 |
| 查询 | 用受限只读 API 查询申请与审计 | 持久化状态、审批人、审计事件与预期一致 |
| 清理 | 按 run_id 清理本轮数据与会话 | 无残留；失败清理任务可追踪 |

只出现“操作成功”提示不满足验收。接口 HTTP 200 也不自动等于业务正确；还要核对业务状态和关联对象。数据准备可以使用 API 提速，但用例要验证的 UI 行为必须实际经过 UI。Playwright 官方明确支持通过 API 准备状态并检查服务端后置条件。[API testing](https://playwright.dev/docs/api-testing)

### 谁提供正确答案

正确性依据按以下顺序选择：已确认的需求验收条件与业务规则；接口契约与领域不变量；经过评审的历史用例。页面当前行为只作为观察结果，不能反过来自动定义预期，否则会把已有缺陷固化为“正常”。

确定性校验覆盖身份、状态、金额、条数、持久化与权限等事实。视觉模型用于解释布局、异常截图或候选目标；只有确需语义评价的内容才使用模型评分，并保留评分标准、证据与人工复核。硬断言失败不能被模型主观评分抵消。

### 资产生命周期

草稿 → 规则与风险评审 → 沙箱复现 → 代码审查 → 稳定性观察 → 回归库 → 维护/退役。

建议新资产至少在独立数据上完成 10 次观察运行，包含 CI 与重置场景，再决定是否进入门禁。该数量只用于发现明显问题，不代表已经证明低偶发失败率。需要用历史缺陷或受控错误验证断言真的会失败，避免测试永远通过。

## 07 确定性执行的工程规范

### 定位与等待

优先依据角色、标签和业务可读名称定位；对重复控件限定表单、弹窗或业务行范围；必要时与研发约定稳定 test id。避免依赖完整 DOM 路径、随机 class 或无语义的序号。必须验证目标唯一，不能用 first() 掩盖歧义。[Playwright Locators](https://playwright.dev/docs/locators)

等待具体事实：元素可见且可操作、请求完成后数据满足预期、状态转移完成。使用可重试的断言，避免靠固定休眠掩盖异步问题；每个轮询必须有明确超时和诊断输出。[Playwright Assertions](https://playwright.dev/docs/test-assertions)

### 数据、账号与依赖

每次运行创建唯一 run_id，数据绑定 tenant_id、case_id 与 attempt；后端清理由这些标识精确限定。清理应可重复调用；进程崩溃时由到期回收机制兜底。并发运行共享账户会造成互踢、列表污染和审批冲突，应按角色与 worker 租用独立账号或证明共享只读会话安全。

浏览器上下文隔离只能隔离 cookies、storage 等浏览器状态，不能自动隔离后端数据。[Playwright Isolation](https://playwright.dev/docs/browser-contexts)

测试会话由凭证管理与执行器注入；认证状态文件可能包含敏感 cookies 等信息，应放在受控临时目录并从版本库排除。需要修改共享服务端状态的测试，应使用适合并行运行的身份与状态策略。[Playwright Authentication](https://playwright.dev/docs/auth)

通知、支付、验证码等外部依赖采用专用测试租户、邮件接收箱或模拟服务；对关键集成保留一组真实测试环境的契约/集成检查。Mock 的范围必须在报告中可见，不能把使用替身的结果称为完整真实链路通过。

### 环境与证据

执行前检查部署版本、依赖健康、数据工厂、账号权限和功能开关；检查失败时保留原因，不进入盲目探索。固定浏览器版本、操作系统镜像、语言、时区、视口和随机种子；需要验证国际化的场景显式参数化。

关键失败保留首次尝试的日志、动作前后截图、断言实测值、业务 ID 和网络摘要。Trace 是诊断工具，不能代替业务断言。对体量较大的普通套件可按失败/重试采集详细 trace；关键试点优先保留首次失败材料，评估额外存储成本。

## 08 Agent 探索、修复与停止边界

### 规划与执行循环

一次探索输入必须包含：业务目标、角色、起始页面、验收规则、允许的数据范围、可用工具、禁止动作以及预算。模型输出结构化动作，执行器只接受 schema 中定义的动作类型与当前页面实际候选。

建议循环为：观察当前页面 → 构造候选 → 选择下一动作或短计划 → 校验权限与前置条件 → 执行 → 验证反馈 → 更新覆盖与预算。每步都做轻量状态检查，但不要求每步都调用大模型；状态偏离、弹窗出现、阶段结束或路径失败时重新规划。该选择综合了 A2 p.9 与 A4 p.14 的不同规划粒度。

DOM 路线先构造包含元素语义、状态和对象标识的候选，歧义时补充视觉；Midscene 路线按视觉接口执行。页面变化后重新验证目标。Deep Agents 拆解业务阶段，页面执行限单步或短流程并统一计量预算；高风险写入还须校验权限、对象和前置状态。

### 先固定探索策略，再看模型表现

主链路阶段验证合法流程与终态；边界阶段围绕必填、长度、数值范围、时间顺序、重复提交和权限规则逐项探索；其他路径阶段只在允许范围内扩展。去重应比较业务目标、状态、动作与断言，不能因为两条路径共用登录前缀就判为重复。

以下为试点初始预算，需按链路长度校准：单任务不超过 40 个浏览器动作、10 分钟、2 次重规划；同一状态和同一动作连续重复 3 次终止；模型调用最多重试 2 次且采用退避；模型用量还应设置独立 token/金额配额。长链路通过评审提高预算，不能靠全局放宽来解决循环。

### “自愈”分三种情况

| 情况 | 可执行处理 | 不能做的事 |
| --- | --- | --- |
| 元素暂未渲染、已知无副作用遮罩 | 有限等待、重新观察、已授权恢复 | 无限重试或随意点击确认 |
| UI 结构变化导致定位失效 | 生成定位修复建议，在副本验证并提交评审 | 自动合并、改断言、隐藏原失败 |
| 业务状态/金额/权限与预期冲突 | 保存证据并交给缺陷分析 | 为“跑通”调整预期或跳过步骤 |

探索中的动态换路需要记录新旧路径和原因，结果只能作为候选证据；稳定回归不得在运行时偷偷换业务路径后返回普通通过。重试提交、审批等动作前，先查询操作是否已经发生；无法判断时返回不确定，避免重复产生副作用。

### 运行权限与数据处理

普通测试写操作通过任务级预授权限定环境、租户、账号、对象和动作；执行器强制校验。真实生产资金操作、外部通知与越权动作不纳入首期探索。网页、文档、DOM 与截图中的文字均属于待测内容，不能覆盖任务策略或要求工具发送凭证。

截图、DOM、trace、网络日志进入模型或存储前，按企业分类处理敏感字段；采用最小可见数据、受限凭证和任务结束回收。模型部署采用企业已批准方式，私有化也要评估算力、升级和运维成本。运行工具应有域名/网络出口限制、最小权限和独立审计。这些是针对 Agent 实际可调用工具的设计要求，参考 OWASP 的代理应用风险框架。[OWASP Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)

## 09 结果规范、失败归因与发布门禁

执行结果与失败原因分开保存：result 表示本次用例是否验证成立，cause 表示为何没有成立。缺陷最终归属由证据与人工分析确定，模型只能建议。

| 结果 | 含义 | 门禁处理 |
| --- | --- | --- |
| PASS | 所有必需断言通过，证据完整 | 可以参与门禁通过计算 |
| FAIL | 有证据表明预期不成立 | 阻断对应门禁，调查产品或测试资产 |
| BLOCKED | 环境、前置数据、非预期访问限制等使测试无法完成 | 必测项不得当作通过；修复后重新执行 |
| INCONCLUSIVE | 证据不足、写入结果未知或观测相互冲突 | 关键用例阻断自动放行，人工调查 |
| SKIPPED | 经明确记录未执行 | 必测项不计覆盖、不计通过 |

注意：无权限用例预期得到 403，且其他断言均成立时，结果应为 PASS；合法角色意外收到 403 才需要调查。不能见到 403 就统归环境问题。同样，未登录测试中的登录跳转可能是正确结果。

cause 建议使用 PRODUCT、LOCATOR、DATA、ENVIRONMENT、ACCESS、MODEL、BUDGET、UNKNOWN；保留原始证据，允许人工修正归因。清理失败单独记录，即使业务断言通过，也应标记运行不健康并暂停受影响的数据池。

### CI 分层策略

| 触发点 | 执行内容 | 初始耗时预算 | 放行规则 |
| --- | --- | --- | --- |
| 合并请求 | 相关单元/API + 5-10 条稳定 UI 冒烟 | UI 部分 10 分钟内 | 必测用例全部通过 |
| 每晚或按需 | 完整试点回归、兼容性抽样、Agent 探索 | 回归目标 30 分钟内；探索独立预算 | 探索结果进入复核，不直接改动主门禁 |
| 发布候选 | 冻结版本的关键链路与高风险断言 | 由试点实测确定 | 必测项全部通过，无未处理的关键风险 |

偶发失败后重试通过必须标记 FLAKY，单独保留首次结果。Playwright 官方区分 passed、flaky、failed；内部再叠加门禁规则，不能仅依赖默认退出码。[Playwright Retries](https://playwright.dev/docs/test-retries)

关键链路首次失败、重试通过时，进入人工归因或修复后独立重跑，不自动变为可信绿灯。非关键 flaky 用例可限期隔离，但必须有负责人、缺陷单、到期时间和替代验证。发布豁免由已有发布责任人决定并留痕，Agent 不签发豁免。

## 10 最小平台能力与日常协作

试点仓库建议按职责分目录：specs 存放需求入口与原文引用；knowledge 存放来源清单、Wiki、本体、正式规则与发布清单；skills 存放 Skill 源包；tools 存放注册定义和适配器；cases 存放用例元数据；tests 存放确定性代码；fixtures 存放数据和身份适配器；exploration 存放探索策略；evals 存放分类评测集；policies 存放执行约束；reports 存放可公开的报告索引。大文件和敏感原文/证据放受控存储，Git 保存授权范围内的元数据与引用。正式规则唯一维护于 knowledge/rules。

每次运行生成可关联的证据包：run_id、case_id、attempt、代码提交或发布制品版本、环境版本、knowledge_release_id、规则版本、Skill/工具版本与哈希、策略版本、模型版本及参数、起止时间、步骤摘要、预期与实测、业务 ID、截图/trace 引用和预算使用量。记录可复核的动作与简要决策依据即可，不需要保存模型内部思维过程。

证据保存期限按内部制度确定；试点可暂定成功摘要 30 天、失败证据 90 天，并在实施前确认。涉及凭证或个人信息的原始材料采用更严格权限与最小留存，不能因为“调试需要”无限保存。

### 一次需求如何流转

产品/业务提出验收条件；LLM 整理 Wiki 与关系草稿，业务/QA 确认规则并发布知识快照；QA 补风险与反例，可选择或自定义 Skill；开发补可测试接口与 test id，测试开发注册工具；任务锁定依赖后生成候选计划和代码，在隔离环境调试；失败由值守人按证据归因；确认缺陷进入既有流程，合格用例经观察后入库，经验回流为知识候选。

| 角色 | 对结果负责的事项 |
| --- | --- |
| 业务/产品负责人 | 规则与验收条件正确，澄清歧义 |
| 业务 QA | 风险清单、覆盖策略、知识与预期复核、纯指令 Skill 创建和调试 |
| 开发 | 单元/API 质量、可测试性、业务缺陷修复 |
| 测试开发 | 本体与规则契约、工具适配器、脚本运行、Skill 模板、回归资产与诊断 |
| 平台/安全支持 | 知识与工具注册发布、环境/凭证、权限、模型接入和数据处理 |
| 发布负责人 | 处理发布例外并承担最终放行决策 |

建议每日处理新增失败与阻断，每周看失败分布、未覆盖风险和维护耗时，每两周决定优先补哪一项基础能力。不要按“谁用了更多 AI”评价人员；评价可复现的交付质量与节省的实际工作。

## 11 如何衡量：同时看覆盖、误判、稳定性和成本

建立冻结的测试集与运行清单，数据按业务链路、优先级、执行模式和版本切分。新增/删除用例、隔离用例、环境中断要单独披露，避免通过改变分母改善数字。以下目标均为内部试点建议，不是行业标准。

| 指标 | 定义与统计边界 | 初始目标或用法 |
| --- | --- | --- |
| 计划执行完成率 | 得到 PASS/FAIL 的用例运行数 ÷ 计划必测运行数；重试不增加分母 | 关键门禁 100%；阻断/跳过显式列出 |
| 风险覆盖率 | 有审核用例与近期有效证据的风险权重之和 ÷ 全部范围内风险权重 | 范围内关键风险 100%；总体目标 ≥90% |
| 首次执行稳定率 | 健康基线版本上首次符合预期的运行数 ÷ 全部计划基线运行数 | 成熟套件目标 ≥98%，按原因拆分 |
| Flaky 率 | 同版本同条件下首次失败、后续通过的运行数 ÷ 全部计划运行数 | 目标 ≤2%；关键项不能以重试放行 |
| 误通过率 | 已知有缺陷样本中被判 PASS 的次数 ÷ 有缺陷评测次数 | 已知关键缺陷样本观测为 0 |
| 误失败率 | 已知正确样本中被判 FAIL 的次数 ÷ 正确样本评测次数 | 目标 ≤5%，同时披露不确定与阻断比例 |
| 生成资产验收率 | 经审核且达到复现/观察要求的独立用例数 ÷ 已完成评审的独立候选数 | 首期测基线，不用生成数量冲业绩 |
| 问题定位耗时 | 从失败报告产生到确认原因的人工分钟数 | 记录中位数与 P90，和同类基线比较 |
| 有效资产成本 | 生成、评审、复现、维护的人工与运行成本 ÷ 新增合格独立用例数 | 比较人工与 AI 辅助的同类任务 |
| 知识质量与维护 | 规则/来源/版本选择正确性、变更影响漏检与审核维护工时 | 用第 17 节专用评测集记录基线，关键错误不得静默进入任务 |
| Skill 与工具可用性 | QA 从草稿到可用的总工时、误启用、契约错误、未知副作用和恢复结果 | 用第 18 节反例验收；不以工具或 Skill 数量代替收益 |

首次稳定率应在已知健康的基线版本观察，产品真实缺陷不能被当成框架不稳定；发布版本报告仍保留真实失败。风险覆盖与测试通过也是两回事：能可靠检出一个缺陷，说明风险有测试覆盖，但该版本并未通过。

### 独立评测集

MVP 先固定 20 个评测任务：8 个已知正确、6 个受控缺陷、6 个环境阻断/证据不足；后续扩展为 40 个任务：20 个已知正确、10 个可复现历史缺陷或受控错误、10 个阻断/证据不足。它们与 12 条 MVP 业务用例以及后续 20-30 条回归资产不是同一个分母。至少保留一部分未用于调提示词的固定评测任务，并包含自审批、跨租户、重复提交、假成功提示和查询不到持久化状态等反例。

各候选模型/策略在同一环境、同一数据与预算下重复执行至少 3 轮，比较结果混淆矩阵、完成率、token、耗时和人工介入。少量样本“零误通过”只表示当前样本未观察到错误，不证明真实误判率为零；同一任务重复也不等于新增独立样本。

### 成本收益计算

月净收益 = 避免的人工回归工时 × 内部小时成本 - 新增评审/维护/运营工时 × 内部小时成本 - 模型/执行/存储增量成本。

一次性建设投入单列；当月净收益为正时，可用“建设投入 ÷ 月净收益”估算简单回收期。缺陷损失减少另行记录，缺乏可靠估值时不折算为收益，避免重复计算。

仅作演算：若每月减少 80 小时重复回归，新增维护等工作 30 小时，内部成本按 200 元/小时、运行成本按 2,000 元/月，则月净收益为 8,000 元；若建设投入 48,000 元，简单回收期约 6 个月。以上不是企业报价、工资或实际收益预测，必须替换为真实记录。

## 12 MVP 开发节奏与分期验收

本节替代原八周工程试点安排。资源假设为 2 名全职 TypeScript 开发、业务 QA 每周约 2 天、运维按需协作。MVP 先覆盖 1 个真实测试环境、1 条链路、12 个代表用例；用户从 Web 完成全过程。

配套《MVP开发任务清单与迭代路线》列出 M01-M28 的职责、依赖和逐项验收，以及后续版本任务。初估开发 43.5 人日，另留约 9 人日联调/发布缓冲；QA 约 8-12 人日、运维约 1-2 人日协作。工期约 6 周，从账号、环境和模型可接入时计算；接入等待单列。只有一名开发时，同范围约 11-13 周，具体按实际吞吐调整。

| 阶段 | 用户可用结果 | 主要开发内容 | 阶段门槛 |
| --- | --- | --- | --- |
| 第 1-2 周 / Alpha | Web 创建任务，后台跑通真实链路和基础结果 | 契约、数据库、授权、队列、知识/工具/数据基础、Playwright 与断言 | 真实浏览器、真实查询、证据可核对；明确仍为内部 Alpha |
| 第 3-4 周 / 受控预览 | 自然语言计划、确认、状态流与基本 Skill 编辑 | Deep Agents TS、Midscene、计划/运行/报告页、文本 Skill | 小范围 QA 试跑；只开放授权、取消和证据已验证的范围 |
| 第 5-6 周 / v0.1 MVP | 完整 Web 闭环和 Skill 调试发布，邀请 5-10 人 | 历史、反馈、取消/去重/回收、目录、反例验证与部署 | 28 项 P0 全完成，下列 MVP 门槛通过 |
| v0.2 / 下一两周 | 知识与工具能由测试团队维护 | Wiki 编辑/摄取草稿、知识发布、Skill 辅助、HTTP/OpenAPI、MCP | 版本、来源、依赖、权限和撤销验证有效 |
| v0.3 / 再两周 | 体验结果沉淀成稳定回归 | 用例候选、TS 代码、评审入库、CI/定时、缺陷平台，扩至 3 条链路 | 稳定回归不依赖 Agent；开始连续稳定观察 |
| v0.4 / 再两周 | 更复杂任务可控运行 | 安全检查点恢复、多 Worker、配额、覆盖探索、模型成本评测 | 故障注入与资源隔离通过，不盲目重放写操作 |
| v1.0 及后续 | 团队推广与持续完善 | SSO、组织/项目、运维；按需求补脚本、共享、本体展示与兼容性 | 主流程和治理达到推广要求；增强项按实测容量继续迭代 |

后续版本按两周节奏滚动拆卡，不能把一个迭代的目标当成全部远期功能的固定交付承诺。每周演示真实任务，每两周复盘用户阻塞点与实际工时。MVP 保留 Web、可信断言、权限、取消与证据；超预算时优先减少用例、工具类型与探索范围。

### MVP 发布条件

1. 受邀测试人员可以从 Web 独立创建、确认、执行、看报告和反馈；5 人验证至少 4 人不需开发者操作终端。
2. 一条真实链路的 12 个代表用例有已确认规则和独立断言，固定基线至少 3 轮；可用业务结论比例目标至少 90%，阻断、不确定、错误、取消和未执行不计成功。
3. 固定 20 项 Agent 评测包含正确、缺陷、阻断/不确定；已知关键缺陷不得误通过，结果披露样本规模。
4. 两模板与一个 QA 自定义文本 Skill 可在 Web 调试并提交发布；知识与工具只使用授权版本；MVP 为 SDK/HTTP，MCP 在 v0.2。
5. 重复提交/投递、页面刷新、Worker 故障、取消、未知副作用和清理失败都能正确留证和结束；不承诺恢复活浏览器原现场。
6. 内部 HTTPS 地址、登录授权、证据权限、费用配额、备份/回退、运行手册和支持负责人齐全。实际响应、规划耗时与运行预算按开发清单验证。

这些是建议验收门槛，尚未取得实测结果。关键误通过、越权或重复业务写入会阻止发布；不能用其他平均指标抵消。

### 推广与完整化验收

v0.3 以后再要求约 20-30 条维护资产、至少 10 个工作日稳定观察、知识变更影响、工具升级/撤销、CI 门禁与成本收益复盘。收益目标和第 11 节指标仍需用真实基线核验，不把 MVP 上线等同于已取得效率收益。

基础回归稳定但 Agent 收益不明确时，保留回归与辅助生成，暂停扩大探索。环境/数据长期造成阻塞时，优先补基础能力。出现关键误通过时停用相应判定策略，补反例并重新评测。跨项目市场、任意脚本自助执行、向量库和复杂本体推理均按明确需求排期。

### 用例评审清单

## 15 Midscene.js 专题：重点试点视觉执行与自然语言测试

### 选型结论与适用位置

**建议把 Midscene 列为首批验证组件，采用 Playwright Test + Midscene SDK 的混合方式。**稳定定位、数据准备、业务查询和关键断言由代码负责；对语义描述更方便的页面操作、复杂视觉控件、辅助视觉判断及有限探索，引入 Midscene。该建议基于能力与需求的匹配，尚无本企业实测胜率或成本数据。

Midscene 的 UI 定位与操作以视觉模型理解截图为基础，支持自然语言任务与单步 API，并提供 Web、移动端等接入方式。它能解决执行和页面理解问题，但仍需企业自行建设业务规则、账号数据、覆盖策略与结果验收。[官方介绍](https://midscenejs.com/zh/introduction)、[模型策略](https://midscenejs.com/zh/model-strategy)

与参考资料 A4 的 DOM/ARIA 候选加视觉选择方案相比，Midscene 的视觉定位路线不同。两条路线可共存于执行适配器：先由已知页面规则选择合适能力，不要假定 Midscene 内部就是 DOM 候选排序；也不要把所有 DOM 可操作页面排除在试点外，应比较编写和维护成本。

### 能力与职责对应

| 能力 | 能做什么 | 企业方案中的边界 |
| --- | --- | --- |
| aiTap、aiInput 等单步 API | 用页面描述定位并执行指定操作 | 外层明确步骤和目标；操作后核对业务对象与状态 |
| aiAct | 将自然语言目标规划为多步操作 | 用于隔离环境的有限探索；外层设置权限、总时长与费用预算 |
| aiQuery、aiAssert | 从当前页面取数，或判断自然语言条件 | 可作页面证据；不能代替持久化状态、权限和审计断言 |
| Playwright 集成 | 对已有 page 创建 Agent，或通过测试 fixture 接入 | 复用现有测试数据、用例组织和 CI，控制接入范围 |
| 报告与用量信息 | 保存过程和截图，提供调用用量信息 | 对接统一 run_id、失败原因、模型版本和费用统计 |

API 语义依据：[基础 API](https://midscenejs.com/zh/basics)、[API 参考](https://midscenejs.com/zh/reference/)、[Playwright 集成](https://midscenejs.com/zh/integrate-with-playwright)。单步 API 中的提示词应描述一个操作目标；条件分支由代码控制，不能把完整流程塞进点击目标描述。aiAssert 的判断仍来自模型对页面的理解，同一模型生成并判断测试时，需要独立业务预期避免相互迎合。

建议一次审批链路这样分工：API 准备申请与角色 → Playwright 登录和进入业务对象 → Midscene 操作代表性复杂控件 → Playwright 核对对象 ID 并执行已授权提交 → 只读 API 验证最终状态与审计 → 汇总两类报告。若需要让 aiAct 处理含写入的整段流程，必须先验证执行层能约束每个动作；缺乏该能力时，应拆成单步调用与已授权业务工具。

平台采用 Deep Agents 时，由其拆解业务阶段、组织知识与分析结果，Midscene 执行单步或短流程。平台统一统计两层模型调用和动作预算，并为每个浏览器会话指定操作者；子 Agent 并行分析日志时，不共享对同一页面的操作权。完整分层和对照验证见总方案第 16 节。

### 三种接入方式的取舍

| 方式 | 适合场景 | 本次建议 |
| --- | --- | --- |
| PlaywrightAgent / Playwright fixture | 已有或准备建设 TypeScript 回归仓库 | 首选；保留现有 runner、数据和业务断言 |
| @midscene/test | 希望用 YAML 编排语义用例，并通过 TypeScript 节点扩展数据与服务操作 | 独立试点；官方当前标为 Beta，先验证 schema、升级与调试成本 |
| 交互式体验或外部 Agent 工具入口 | 熟悉能力、验证提示词与页面可操作性 | 用于发现候选场景，产物达到复现与验收要求后再入库 |

Midscene Test 将语义节点与类型化自定义节点结合，但 Beta 状态意味着接口和使用方式仍可能变化。本期不把它设为已有回归仓库迁移的前提。[Midscene Test 概览](https://midscenejs.com/zh/midscene-test/overview)、[扩展自定义节点](https://midscenejs.com/zh/midscene-test/extend)

### 必须验证的行为差异

这些细节来自官方文档，应在锁定依赖版本后重测，而非直接照抄示例配置。

1. **新标签页：**Playwright 集成默认启用 forceSameTabNavigation，会把新标签页导航转到当前标签页。测试产品真实跳转行为时关闭该选项，并显式管理新 page 或验证 BrowserAgent 的跟随策略。
2. **原生下拉框：**默认 forceChromeSelectRendering 会调整 Chrome 原生 select 的呈现。测试原生外观和行为时关闭并建立对应基线；普通表单可直接使用 Playwright 的标准选择操作。
3. **浏览器差异：**部分能力依赖 Chromium/CDP；不能因为 Playwright 支持多个浏览器，就推定 Midscene 所有能力在 Firefox/WebKit 一致。先锁定 Chromium 主路径，兼容测试按能力清单验证。

以上依据：[Playwright 集成的浏览器行为说明](https://midscenejs.com/zh/integrate-with-playwright)。示例中的固定等待、启动参数与模型名称也需按企业环境调整，不能当作生产模板。

4. **上下文不是叠加规则：**调用级 context、API 级 aiContexts 和默认 context 按优先级选用，并非自动合并。关键约束放到可执行策略中，避免局部上下文覆盖后丢失。[基础 API 上下文配置](https://midscenejs.com/zh/basics)
5. **规划次数不是总预算：**replanningCycleLimit 限制重新规划次数；总动作数、调用次数、token、金额和任务墙钟时间仍需平台独立控制。[Agent 参数与用量回调](https://midscenejs.com/zh/reference/)

### 缓存能提速，但不能当作离线确定性回放

Midscene 缓存包含规划结果与 Web 定位快捷路径。缓存失效或未命中时仍可能调用模型；aiQuery、aiAssert 等页面理解 API 不缓存结果。read-only 表示缓存读写策略，不代表禁止模型推理；也不能据此宣称回归不再受模型变化影响。[缓存机制](https://midscenejs.com/zh/caching)

本项目建议分别记录冷缓存、热缓存、失效回退的耗时和费用。按用例、角色、应用版本和依赖版本划分缓存命名空间；禁止将未知来源的缓存直接作为发布依据。Canvas 等页面不能期待 XPath 快捷路径获得同样收益。缓存流程执行到一半后失效时，先确认已发生的业务副作用，再决定是否继续或重启。

稳定回归如果要求完全不调用模型，应落为经过审核的确定性代码路径，并在运行记录中验证模型调用数为零。把缓存策略改成 read-only 不能实现这个要求。

### 模型、数据与报告接入

模型选择先验证企业获准的多模态服务对截图定位的效果；需要内网部署时，再比较可自托管的视觉模型与现有推理基础设施。接口形式兼容并不保证坐标、图像输入和返回格式满足 Midscene。先运行固定版本 CLI 的模型验证，再在真实代表页面比较，不直接引用官网其他平台的成功率作为本项目指标。[模型配置](https://midscenejs.com/zh/model-common-config)、[模型调试与可观测性](https://midscenejs.com/zh/model-debugging-observability)

SDK 在本机运行与模型推理在内网是两回事。官方说明页面截图等数据会发送到配置的模型服务。实施时画清浏览器、模型网关、推理服务、trace 和报告的真实数据路径；使用测试数据，限制报告访问，核对配置覆盖后的实际 endpoint。[数据隐私说明](https://midscenejs.com/zh/data-privacy)

推荐从一个多模态模型开始；只有规划或信息提取出现明确瓶颈时，再评估拆分 Planning/Insight 模型。报告可导出结构化内容用于内部汇总，但“报告里有操作成功”不能直接映射业务 PASS；应绑定独立断言和缺陷证据。[模型策略](https://midscenejs.com/zh/model-strategy)、[报告消费工具](https://midscenejs.com/zh/consume-report-file)

### 对照试验与采用条件

MVP 先完成一个代表控件的单步接入与 20 项基线评测，不将下面完整对照作为上线前置；在后续扩展阶段，从总方案第 11 节的 40 个评测任务中抽取 12 个：6 个正常任务、4 个已知缺陷任务、2 个环境或权限阻断任务。比较纯 Playwright、Playwright + Midscene 单步混合、受限 aiAct 三种方式；每个组合重复 3 次，共 108 次计划运行。该规模是试验设计，不是已完成实测。另挑少量流程做冷/热/失效缓存对照，单列运行数和预算。

| 场景组 | 故意设置的变化或问题 | 应取得的证据 |
| --- | --- | --- |
| 普通表单与审批 | 文案变化、列表重排、多个同名按钮 | 操作的是指定业务对象，不能仅验证点击完成 |
| 视觉复杂页 | 小控件、滚动、弹层、Canvas 或图形选择 | 成功率、定位误差、重试和人工维护时间 |
| 真实浏览器语义 | 新标签页、原生 select | 开关前后行为差异与适用配置 |
| 已知业务缺陷 | 页面提示成功但后端未改变、权限错误 | 独立断言应失败或标记阻断，禁止误通过 |
| 恢复与缓存 | 模型超时、流程部分写入、缓存失效 | 无重复提交，回退过程和额外调用可追溯 |

采用条件：关键缺陷样本无观测到的误通过；无越权或错误对象写入；正常与阻断任务分类可解释；端到端人工工时降低；p50/p95 时延、每个有效用例费用与维护成本在试点预算内。小样本结果不能证明真实误判率为零。只在达到条件的场景推广，DOM 定位已经便宜稳定的部分继续保留。

## 16 Agent 开发框架选型：用显式流程承载可恢复任务

### 本次选型对象与推荐

这里选的是**开发企业内部 UI 测试 Agent 平台的运行与编排框架**，包括规划、执行、判定、人工复核和资产沉淀。开发者日常使用的编码助手属于另一类采购与使用决策。

首选验证 **Deep Agents（基于 LangGraph）+ Playwright Test + Midscene SDK**。Deep Agents 作为应用开发入口，负责知识使用、任务拆解、上下文管理、用例生成和失败分析；LangGraph 承担底层状态与运行能力，需要精细控制的阶段再使用显式流程。MVP 采用 Deep Agents TS 实施；直接 LangGraph 与 Mastra 保留为遇到明确障碍时的替换路径，不要求先完成多框架竞赛。

本项目已确认采用 TypeScript：Web、API、Agent 和浏览器 Worker 共享语言与契约；核心链路不增加 Python 服务。以下其他语言框架保留为调研记录，当前不再作为并行选型任务。采用 Deep Agents 是工程路线选择，尚未证明其时延、成本或成功率优于其他方式。[Deep Agents 官方介绍](https://docs.langchain.com/oss/javascript/deepagents/overview)

### 先分清四个层次

| 层次 | 负责的问题 | 首期建议 |
| --- | --- | --- |
| Agent 应用与编排 | 知识使用、任务拆解、上下文、暂停恢复和结果汇总 | Deep Agents 作为入口；基于 LangGraph 运行，关键阶段按需使用显式流程 |
| UI 与业务执行 | 浏览器会话、页面动作、数据准备、结果查询 | Playwright + Midscene + 企业适配器 |
| 任务基础设施 | 排队、并发配额、租约、超时、取消、清理 | MVP 使用独立 Worker 与持久队列；稳定回归后续接入 CI |
| 观测与评测 | 证据、模型调用、费用、反例集、人工结论 | 独立 run_id 与统一结果协议，便于替换框架 |

MCP 是工具接入协议，不能替代这四层。LangGraph 的检查点也不能替代浏览器资源管理。MVP 在同一 TypeScript 仓库管理模块，Web、API 与 Worker 分进程部署；浏览器执行从第一版起脱离 HTTP 请求生命周期。

Deep Agents 已使用 LangGraph 的运行基础，不必为每个任务再套一层执行同样规划工作的外层 Agent。业务策略、预算、执行接口和独立断言保持程序控制。

### 为什么优先采用 Deep Agents 开发应用

完整平台既要执行受控流程，也要阅读需求、组织文件资产、处理长日志和分析失败。Deep Agents 预先组合了这些任务需要的通用 Agent 能力，有望减少直接使用 LangGraph 时的重复开发；具体收益仍需同任务对照。[定制能力](https://docs.langchain.com/oss/javascript/deepagents/customization)

| 平台任务 | 可复用能力 | 本项目实现要求 |
| --- | --- | --- |
| 阅读需求、规则和历史缺陷 | Skills 提供方法指引，文件或工具按需获取知识 | 读取已审核 Wiki/本体/规则快照；关键依据绑定业务域、来源和版本 |
| 长流程探索与诊断 | 历史压缩、大型工具结果转存 | 业务对象、硬断言、预算与证据引用独立保存，不能只放摘要 |
| 生成测试代码与报告 | 文件读写和可配置存储后端 | 生成资产进入候选区；经审核后才进入回归库 |
| 分析相互独立的材料 | 上下文独立的子 Agent | 先用于需求或日志分析；浏览器任务明确单一操作者 |

能力依据：[Skills](https://docs.langchain.com/oss/javascript/deepagents/skills)、[上下文管理](https://docs.langchain.com/oss/javascript/deepagents/context-engineering)、[存储后端](https://docs.langchain.com/oss/javascript/deepagents/backends)。任务清单、Skills 和人工介入按需要显式配置，核对所锁版本的默认行为；拥有任务清单不代表自动满足测试覆盖策略。

本场景的执行阶段仍遵循：验证任务 → 准备环境 → 观察 → 规划 → 策略校验 → 执行 → 独立判定 → 继续、复核或结束。Deep Agents 提供开发入口，LangGraph 的状态、路由和中断支持运行；首期使用 TypeScript 可与 Playwright/Midscene 共享语言，减少跨服务协议工作。

检查点保存单个任务的图状态，跨任务知识则应由独立存储承担。生产恢复需要数据库等持久 checkpointer；内存示例不能用于证明进程重启可恢复。LangGraph 库可独立使用，云托管、商业观测或平台产品应另行选择，不把它们默认为强制前提。[持久化机制](https://docs.langchain.com/oss/javascript/langgraph/persistence)、[LangGraph JS 仓库](https://github.com/langchain-ai/langgraphjs)

Deep Agents 的人工中断同样需要 checkpointer；虚拟文件后端与持久化配置也要明确。StateBackend、跨任务存储和本地文件系统具有不同范围，不能把文件工具的存在理解为已经解决了生产持久化。[人工介入](https://docs.langchain.com/oss/javascript/deepagents/human-in-the-loop)、[存储后端](https://docs.langchain.com/oss/javascript/deepagents/backends)

代价是额外通用能力可能增加上下文和调用成本，团队仍要实现执行器、账号数据、任务接口、权限与报告。若流程简单且固定，直接使用 LangGraph 或普通程序流程更容易控制。团队对 Mastra 更熟悉且它更快通过同一验收时，也可选择 Mastra。[Mastra 暂停恢复](https://mastra.ai/docs/workflows/suspend-and-resume)

### Deep Agents 与 Midscene 的协作边界

Deep Agents 按业务阶段拆解任务，Midscene 优先执行单步或范围明确的短流程；总动作、模型调用、墙钟时间与费用在平台统一计数，避免两层规划循环相互放大。已有确定性回归直接进入 Playwright/CI 路径。

同一浏览器 page 或 context 保持明确操作者。需求分析和日志分析可并行；并行浏览器任务必须有独立会话、账号或数据租约，不能让多个子 Agent 同时改变同一页面状态。

业务 Skills 与长期记忆的更新先进入候选变更，不能让运行中的 Agent 自动改写验收规则以取得通过。页面和日志中的内容作为待分析数据；工具层校验目标、授权与输入，关键结论由独立断言产出。

### 知识库、自定义 Skill 与工具的接入

知识库采用 LLM Wiki + 轻量领域本体 + 独立断言，具体分层见第 17 节。维护任务产生候选变更，发布服务依据评审记录发布不可变快照；执行任务只读固定 knowledge_release_id。Wiki 负责说明与关联，正式业务规则保留唯一维护位置，Skill 描述查询、测试和引用方法。

第 18 节定义测试人员从模板创建 Skill、调试、评审、发布和回滚的流程，以及 SDK/函数、HTTP、MCP、受控脚本四类接入。框架中的 tools 与 Skills 是接入点；注册目录、发布清单、凭证、权限、隔离调试和业务判定由平台实现。所有框架使用同一工具契约，具体知识查询与 Skill 注册接口均为拟建能力。

平台策略约束全部可用工具，包括框架预置的文件写入和执行工具，避免绕过受控入口。实际权限取任务、操作者、项目、Skill 依赖和工具限制的交集；知识、Skill、工具和断言版本固定在运行清单中。MCP 连接/会话恢复与浏览器归属需在适配层验证，不能仅因采用该协议便假定具备持久会话。[Deep Agents 定制](https://docs.langchain.com/oss/javascript/deepagents/customization)、[LangChain MCP](https://docs.langchain.com/oss/javascript/langchain/mcp)

### 平台最小设计与恢复语义

首期按职责划分模块，不必让每个职责都变成一个独立聊天 Agent。一个规划模型配合策略节点、执行适配器和独立判定器，已经能实现探索闭环。确定性回归可以走不调用模型的独立路径。

建议状态记录：run_id、tenant_id、case_id、应用/模型/提示词版本、knowledge_release_id、Skill/工具/断言版本与哈希、当前节点、已确认业务对象 ID、步骤与预算计数、执行租约引用、最近证据、审批记录引用、终态与失败原因。截图和 trace 放受控对象存储；不要把活的 Playwright page、浏览器进程句柄、密码或完整会话凭证塞进图状态。

建议工具契约：任务和动作 ID、受限目标、输入 schema、调用期限、幂等键、结果状态、业务对象引用、证据引用。所有候选框架使用同一契约，模型厂商与编排框架可以分别替换。

**检查点恢复不等于浏览器恢复，更不等于业务副作用仅发生一次。**LangGraph 中断恢复会从对应节点开头重新执行，中断前的代码可能再次运行。[中断与恢复规则](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

以“提交审批后 worker 崩溃”为例：恢复时先校验身份、租约与环境版本；查询该业务对象是否已经审批，并用审计事件或幂等键确认本次动作；已完成则补记证据并继续，未完成且可安全重试才执行；无法判断时进入人工复核或不确定终态，不能直接再点一次。浏览器已丢失时重建上下文并验证当前页面与对象，不按旧截图坐标盲目回放。

人工介入仅出现在企业策略要求或任务确有歧义的节点；已获任务预授权的普通测试操作直接执行。审批引用应绑定任务、租户、动作目标、计划版本和有效期；恢复接口重新验证操作者与审批状态，避免旧批准被用于新对象。取消必须同步停止执行、回收浏览器和账号租约、触发清理；在最终报告中区分任务取消与产品失败。

### 已确定语言与历史备选路径

| 现有条件 | 推荐组合 | 调整理由 |
| --- | --- | --- |
| 本项目：Web 入口与核心 TS 已确认 | Deep Agents TS（基于 LangGraph）+ Node 执行模块 + Playwright/Midscene | 复用通用 Agent 能力并减少跨语言边界 |
| Python 平台和模型工程积累明显 | Deep Agents Python + Node 执行服务 | 复用团队积累；仅传工具契约和证据引用，不传浏览器对象 |
| 流程固定且需要精细控制 | 直接使用 LangGraph + 同一执行适配器 | 对照验证省去通用 Agent 能力后的成本与维护收益 |
| TS 团队已有 Mastra 经验 | Mastra + 同一执行适配器 | 让维护经验和相同验收结果影响最终决定 |
| .NET / 微软平台是企业主栈 | Microsoft Agent Framework + Node 执行服务 | 优先复用现有身份、部署和维护能力；核对具体语言支持 |
| 需求仅为少量固定回归与一次性生成 | CI + Playwright/Midscene + 普通程序流程 | 先交付测试资产，暂不增加复杂编排平台 |

持久执行引擎属于另一个选择层。Pydantic AI 当前官方列出 Temporal、DBOS、Prefect、Restate 等集成；若采用这些组合，需要把引擎服务、故障恢复和运维成本一并核算。没有跨长时段任务和分布式执行需求时，不为“架构完整”同时引入多套状态系统。[Pydantic AI 持久执行](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/)

依赖许可按固定版本和实际使用组件记录。LangGraph JS 仓库标为 MIT；Mastra 当前核心以 Apache-2.0 发布，但 ee 目录有单独企业许可，不能笼统说所有功能均可免费用于生产。框架、云服务、模型和报告托管分别核算费用与部署边界。[LangGraph JS](https://github.com/langchain-ai/langgraphjs)、[Mastra 仓库许可说明](https://github.com/mastra-ai/mastra#licensing)

### 实施验证与触发式框架对照

MVP 将结构化输出、权限、预算、取消、幂等与证据验证纳入 M09/M16/M21/M26，先交付一个真实可用闭环。持久检查点安全恢复在 v0.4 的 O01 交付；MVP 对浏览器进程丢失明确终止、保存证据并核对未知副作用，不承诺原现场恢复。

仅当 Deep Agents 的恢复、接口或开销不能满足验收时，再用同一工具契约实现“Deep Agents TS + 执行器”和“直接 LangGraph TS + 同一执行器”两个薄原型。固定模型、输入、任务、工具、预算和业务判定标准，对比总开发维护工时、误判、恢复行为、时延和调用费用；同时记录直接 LangGraph 版本尚未实现的能力，避免把功能缺失误算为性能优势。Mastra 在首轮结果不满足需求或团队已有积累时再验证。

该可选框架对照建议预算约 3 个开发人日；触发后单独排期，复用浏览器和数据适配器，环境接入时间单列。该预算只覆盖有限原型，不代表完成全部平台功能和生产验收。

| 验证阶段 | 需要证明的行为 | 交付证据 |
| --- | --- | --- |
| 第 1 个开发人日 | 同一任务能完成准备、执行、业务判定和报告；输出校验有效 | 两个原型的变更、依赖锁定、相同任务结果 |
| 第 2 个开发人日 | 中断后恢复、写入后崩溃、模型超时、用户取消均按预期处理 | 故障注入日志；无重复业务写入；清理记录 |
| 第 3 个开发人日 | 重复恢复请求、权限/租户隔离、费用限制、版本不匹配能被拦截 | 重复请求与越权反例；预算统计；问题与修复工时 |

为 Deep Agents 增加三项代表性检查：长日志导致上下文压缩后仍保留正确业务对象与验收条件；子 Agent 只取得分配给它的工具和任务范围；委派与 Midscene 调用全部纳入总预算。重复提交、错误对象写入和断言被改写均不得发生。

知识与 Skill/工具扩展另按第 17、18 节验收：锁定版本、工具 schema 漂移、缺失依赖、跨项目知识、Skill 误启用及发布回滚。按开发清单交付：MVP 提供知识快照、文本 Skill 与 SDK/HTTP；v0.2 扩展知识编辑和 MCP。其工作不计入上述可选三人日对照预算。

权限、幂等、取消和证据底线有一项无法满足，则实现不能进入用户试用；需要选型对照时再使用以下权重。通过后按建议权重比较：恢复与控制 30%、团队开发维护成本 25%、Playwright/Midscene 集成 20%、模型与部署适配 15%、观测和资产导出 10%。权重可在评审时修改，评分必须附运行证据或工时记录；本报告不预填虚构分数。

最后形成一页决策记录：选定框架和确切版本、选择原因、保留的替换接口、未解决问题、实测成本、复评触发条件。触发条件包括团队语言变化、恢复缺陷、依赖升级破坏兼容、费用超预算及新增终端需求。当前落地路线固定为 TypeScript + Deep Agents，只有验收证据表明存在不可接受障碍时，才启动有记录的替换决策。

## 17 知识库：LLM Wiki、轻量领域本体与独立断言

### 建设结论与职责

采用 **LLM Wiki + 轻量领域本体 + 独立断言**。LLM Wiki 负责整理与维护可阅读的知识；本体统一概念、稳定标识和关系；版本化规则与程序断言提供测试依据。首期用 Markdown、YAML/JSON、Git 和结构化查询形成闭环，向量数据库、完整 OWL 推理栈及图数据库不作为首期前提。

LLM Wiki 是知识管理模式：保留原始资料，持续生成关联页面，并维护索引、来源和变更记录。Karpathy 原文描述的是模式而非产品，本项目在此基础上增加审核、版本和权限设计，不采用模型对正式知识无限制改写的方式。[LLM Wiki 原始方案](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

本体建模、Wiki 与检索承担不同职责。Wiki 双链需配合明确的概念类型与关系校验，才可支持精确的依赖查询；本体也不能自行保证场景覆盖。RAG 可以使用文件、数据库或图查询，不仅限于向量检索；Wiki 增长后可增加关键词或语义检索，并用实际任务验证收益。[LangChain 检索说明](https://docs.langchain.com/oss/javascript/deepagents/retrieval)

### 知识分层与首期存储

以下目录是建议布局，名称均为仓库相对路径。原始资料、规则、本体与测试资产各有唯一维护位置；Wiki 引用这些内容，不另存一份可独立修改的验收标准。

| 层次 / 位置 | 内容与权威范围 | 首期维护方式 |
| --- | --- | --- |
| 原始资料：knowledge/raw | 需求、契约、制度、缺陷记录的版本快照；为结论提供来源 | 保存来源 ID、版本、定位与摘要哈希；新版本追加，保留旧记录。大文件与敏感附件使用受控存储引用 |
| 领域 Wiki：knowledge/wiki | 对象、角色、流程、测试方法、经验与来源解释 | Markdown 页面、index、追加式 log；由 LLM 生成草稿，经校验和评审发布 |
| 轻量本体：knowledge/ontology | 概念类型、稳定 ID、类型化关系与允许的字段 | YAML/JSON 描述，schema 与引用完整性校验；维护者审核模型结构变更 |
| 正式业务规则：knowledge/rules | 适用条件、预期、不变量、优先级、来源与有效版本 | 业务/QA 确认，作为断言依据；与 Wiki 冲突时停止并处理冲突 |
| 执行资产：cases、tests、fixtures | 用例、可执行断言、数据准备与清理适配器 | 测试开发维护；关联规则 ID 和版本，代码评审与反例验证 |
| 发布与评测：knowledge/releases、evals/knowledge | 发布清单、兼容版本、查询与变更反例集 | 发布快照不可变；记录审核、依赖和回滚目标 |

现有 specs 用于需求入口与原文引用，已确认的可执行验收规则统一归入 knowledge/rules，避免 specs 与规则库同时成为可写的正确答案。Wiki 中的概括、模型推断和未解决问题分别标注，不把推断自动升级为业务规则。

### 业务本体与测试本体的连接

首期围绕申请审批建模，再将验证过的公共概念扩展到另外两条链路。

| 概念范围 | 代表概念 | 代表关系 |
| --- | --- | --- |
| 业务领域 | 业务对象、角色、流程、状态、动作 | 角色执行动作；动作作用于对象；动作具有前置状态和后置状态 |
| 规则与来源 | 业务规则、需求条款、接口契约、版本 | 规则约束动作；规则来源于条款；新规则替代指定旧版本 |
| 测试领域 | 风险、场景、用例、断言、数据工厂 | 用例覆盖规则；断言验证预期；用例依赖数据工厂 |
| 执行与证据 | 页面组件、业务 API、运行、证据 | 业务动作映射工具；运行执行用例；证据支持某次断言 |

关系名、两端允许的类型和基数由 schema 明确定义。规则到用例的覆盖关系可用于查漏；运行记录另存实际 PASS/FAIL/BLOCKED 等状态，不能用“有一个用例链接”代替有效覆盖或通过结论。状态迁移、组合与边界覆盖需要独立的覆盖策略。

本体采用开放语义时，缺少某事实不能直接推断为假。若后续采用 RDF/OWL，SHACL 可校验图结构和显式条件；时序、业务写入与权限结果仍由专门的规则和程序断言验证。[OWL 语义](https://www.w3.org/TR/owl2-primer/)、[SHACL](https://www.w3.org/TR/shacl/)

### 页面、规则与发布清单的契约

每张知识页面至少记录稳定 ID、类型、业务域、适用应用版本、来源定位、关系、负责人、审核状态、更新时间与替代关系。来源定位应能落到需求条款、文档页码或代码提交，不能只链接到一个大型目录。资料密级与项目权限随页面和索引传播。

示例为平台自定义元数据草案，不是 Deep Agents 的内置 schema；下列编号均为演示数据。

```yaml
id: WIKI-APPROVAL-SELF
type: test_scenario
domain: approval
status: draft
owner: pilot_qa_owner
source_refs: [DEMO-SPEC-01@v1#section-3]
rule_refs: [DEMO-RULE-SELF@v1]
relations:
  covers: [DEMO-RISK-SELF]
  uses_case: [DEMO-CASE-SELF]
unresolved_questions: []
```

发布清单固定 knowledge_release_id、原始来源版本、Wiki/本体/规则哈希、审核记录、兼容应用版本及用例/断言制品引用。发布前验证所有依赖可解析；运行时再与实际测试制品匹配。目录别名可以指向最新版本，但任务开始后必须解析为不可变的具体版本。

### 编写、发布与运行分离

知识维护流程：收录原始资料快照 → LLM 生成页面和关系变更草稿 → 程序 lint → 业务/QA 复核规则与冲突 → 发布不可变快照 → 标记受影响用例 → 对受影响资产重新验证。

程序 lint 检查字段、来源、断链、重复 ID、状态和版本匹配；LLM 辅助发现表述矛盾，但不能独自证明知识真实。来源变更通过反向引用标记关联页面和用例待复核，不能只更新概要而保留过期预期。多位作者通过分支和差异合并协作，发布使用一致的快照清单，避免读取半更新目录。

运行任务只能读取已授权且已发布的快照；知识维护身份只能写候选区，不能凭模型输出发布规则。发布服务依据评审记录完成晋级。新发现以候选形式回流，不改变当前任务的验收条件。需要例外规则时先完成规则确认并创建新的计划或任务版本。

查询先按项目、业务域、权限、应用版本和知识版本过滤，再读取页面或扩展关系。共享索引、摘要和工具返回值同样执行过滤。涉及敏感原文时只返回授权片段或证据引用，凭证保存在企业凭证服务中。原文中的指令作为资料内容，不授予新的工具权限。

### Deep Agents 如何访问知识

Skills 描述“如何查知识、如何设计场景、如何引用证据”；业务规则留在规则库。知识库通过文件或自定义工具按需读取，避免将全部知识塞入系统提示词。任务的知识版本与关键规则 ID 独立保存，不能仅依靠上下文摘要。[Deep Agents Skills](https://docs.langchain.com/oss/javascript/deepagents/skills)

| 拟建接口 | 输入与返回 | 运行约束 |
| --- | --- | --- |
| knowledge.search | 查询文本、业务域、release_id；返回命中页面、版本与来源 | 先过滤授权范围；返回限量摘要和引用 |
| knowledge.get_rule | 规则 ID、release_id；返回适用条件、固定预期、来源与审核状态 | 校验正式状态及应用版本，不回退到任意相似规则 |
| knowledge.get_flow | 流程 ID、release_id；返回状态、动作、角色与关联规则 | 按关系类型扩展，并限制深度与数量 |
| knowledge.get_impact | 变更 ID、基准/目标版本；返回关联页面、用例与断言 | 基于已登记依赖计算影响，披露未知和未建模依赖 |

上述为本平台待开发工具，不是框架默认能力。接口统一纳入第 18 节工具目录与权限校验。关键规则缺失、冲突、失效或版本不匹配时，该用例记为知识前置条件阻断；业务证据不足按结果规范记为不确定。不能使用当前页面行为猜测“正确答案”。

### 一次审批测试如何使用

用户输入“验证申请人不能审批自己”，平台锁定知识版本和测试角色。Agent 读取流程、规则与历史用例，输出关联规则 ID 的候选计划；覆盖策略检查正常审批、自审批、无权角色和非法状态等适用场景。

执行器使用本次任务的数据，经 UI 尝试自审批；独立断言按已确认规则检查请求是否被拒绝、业务状态是否未改变以及是否没有产生成功审批记录。报告同时保留规则来源、知识版本、实际证据和结果，避免只看拒绝提示。若产生“拒绝事件是否也必须审计”的新问题，应登记为待确认事项，不临时补写规则。

业务规则发生变化时，知识维护流程提交新草稿并给出受影响用例清单；旧运行继续引用旧快照，新运行使用经过评审的新快照。确认后的测试经验可以进入 Wiki，但不能用失败结果自动覆盖验收依据。

### 试点验收与后续扩展

MVP 第 1-6 周交付一条链路的最小知识快照、授权查询和 Web 阅读/规则引用，对应开发清单 M10/M20/M25；资料整理和发布可由维护者通过版本化导入完成，普通测试人员的使用流程全部在 Web。v0.2 的 K01/K02 补齐 Web 编辑、LLM 摄取草稿、评审发布、回滚与变更影响；E05 完成本体与覆盖可视化。以下检查按对应能力进入的版本验收，资源以《MVP开发任务清单与迭代路线》为准。

| 检查项 | 验证方式与首期要求 |
| --- | --- |
| 来源可追溯 | 范围内关键规则均有可定位来源、负责人和评审记录；每次运行记录知识版本 |
| 查询与覆盖 | 用人工标注的代表任务检查规则命中、版本选择、来源准确性和覆盖缺口，披露漏检与误检 |
| 变更影响 | 注入规则替代、删除、断链和跨页面冲突；相关资产进入复核，不能静默沿用旧规则 |
| 运行隔离 | 反例集中草稿、错误版本及无权知识均不能进入正式任务，历史任务快照可重现 |
| 判定独立 | 真实失败不触发自动放宽规则；缺失关键依据可明确阻断并给出原因 |
| 维护收益 | 对照直接阅读原文的同类任务，统计编写、审核、查询、修订总工时及模型费用，不预填节省比例 |

知识评测集单独标记，不能混入业务测试成功率的分母。首期记录查询基线；覆盖依赖未建模完整时，影响清单不能宣称穷尽。Wiki 更新、人工校核和重建索引的成本计入总成本。

当目录索引和关键词检索出现持续漏检或延迟超标，再对同一评测集比较全文与语义检索；当类型化关系查询成为主要瓶颈，再比较关系库与图存储；存在明确的形式化推理需求时，再评估 OWL/规则引擎。采用任何扩展都保留来源、权限和版本契约。

## 18 测试人员自定义 Skill 与工具接入

### 产品目标与能力分工

测试人员可以将反复使用的测试方法做成 Skill，从工作台选择模板、填写适用场景、关联知识与已接入工具，调试后发布给项目使用。测试开发可以补充脚本和适配器，平台维护者管理工具连接、凭证和运行权限。

| 对象 | 负责什么 | 本平台边界 |
| --- | --- | --- |
| 知识库 | 业务事实、流程、规则和依据 | 正式任务只读已审核快照，见第 17 节 |
| Skill | 何时使用某方法、步骤、工具协作和输出要求 | 可生成候选计划，不能自行授予权限或改写业务预期 |
| Tool | 一个有输入输出契约的具体能力 | 实际执行前校验身份、环境、对象、预算与副作用 |
| Workflow | 固定的步骤、分支、暂停和恢复顺序 | 必须固定执行的步骤用程序控制，不仅写在 Skill 提示词里 |
| 测试用例 | 一组可重复的准备、动作、预期与清理 | 关联正式规则和可执行断言，支持独立进入 CI |

Agent Skills 规范以 SKILL.md 的元数据和正文为基础，可携带 references、assets、scripts 等资源。Deep Agents 可按需加载 Skills；本平台在其上增加注册、版本、调试和发布机制。[Agent Skills 规范](https://agentskills.io/specification)、[Deep Agents Skills](https://docs.langchain.com/oss/javascript/deepagents/skills)

### 测试人员的创建与使用流程

工作台提供“技能库、编辑器、调试台、工具中心”四个入口。MVP 必须提供 Web 文本 Skill 模板、编辑、调试和提交发布，普通 QA 不需要操作仓库；工具目录先只读展示与健康检查，新增适配器由维护者注册。完整自助连接和跨项目分发按后续迭代交付。

| 使用步骤 | 用户操作 | 系统呈现与产出 |
| --- | --- | --- |
| 创建草稿 | 从权限测试、表单边界或流程验证模板复制；也可用自然语言生成初稿 | 适用/不适用条件、参数、知识引用和待补信息 |
| 编写与绑定 | 编辑步骤、选择正式规则和工具、指定预期输出 | 依赖是否可用、是否需要新的连接或授权；显示版本差异 |
| 调试 | 提供样例输入，选择隔离数据和调试环境 | Skill 是否被选中、规则与工具版本、调用轨迹、业务断言、耗时与费用 |
| 发布 | 提交变更说明及验证结果，按项目流程评审 | 不可变版本、内容哈希、适用范围、维护人和回滚版本 |
| 使用 | 在任务中手动选择 Skill，或允许系统推荐 | 手选优先；展示最终选用版本和关联知识，不暗中启用无关技能 |
| 维护 | 根据失败反馈改草稿、废弃旧版本 | 影响哪些任务模板和用例，兼容问题及迁移建议 |

业务 QA 可编写纯指令 Skill、关联已授权工具，并在允许的隔离环境调试。新建外部连接或引入可执行代码由工具维护流程处理。代码型 Skill 的脚本必须登记为受控工具或在批准的隔离运行器执行；上传 scripts 目录不意味着自动获得主机执行权。

### Skill 包、元数据与依赖

每个包使用稳定的组织/项目 ID，显示名称可修改。SKILL.md 保持标准格式；平台的权限、发布和依赖信息存入注册记录，导出时可附 platform.yaml。后者是本项目定义的清单，不是 Agent Skills 或 Deep Agents 的内置字段。兼容性要求与版本范围在发布时解析为确切制品和哈希。

| 注册信息 | 必须说明的内容 |
| --- | --- |
| 身份与归属 | skill_id、版本、负责人、项目、状态、内容哈希 |
| 输入输出 | 输入 schema、必填参数、输出 schema；示例与异常输出 |
| 知识依赖 | 业务域、规则 ID、兼容知识版本；具体任务锁定 knowledge_release_id |
| 工具依赖 | 注册工具 ID 与版本、必要/可选能力、浏览器会话使用方式 |
| 运行范围 | 环境、对象范围、允许的副作用、最大调用次数与总预算 |
| 质量与发布 | 正例、反例、最近验证结果、评审记录、回滚目标 |

一个示例 Skill 的正文可以这样写。编号为演示数据，工具需先按下节实现；示例表达工作方法，不声称这些操作已存在。

```markdown
---
name: approval-permission-check
description: 验证申请审批中的自审批与角色权限，适用于已接入的审批测试环境。
---

读取任务锁定版本中的审批规则，列出规则 ID 与来源。
使用已登记的数据工具准备专用申请、角色和业务对象。
通过 UI 执行允许范围内的审批尝试，保留操作与返回证据。
调用业务查询和独立断言，核对拒绝结果及未改变的业务状态。
规则缺失则返回知识阻断；提交结果未知则先查询，不盲目重放。
输出场景、规则、预期、实际、证据与清理结果。
```

标准中的 allowed-tools 仍是实验字段，平台可以解析作为意图提示，但实际权限以服务端策略为准，不能依赖某客户端是否执行该字段。[Agent Skills 字段定义](https://agentskills.io/specification)

### 工具中心与接入类型

接入流程：登记负责人和用途 → 选择适配方式 → 定义输入/输出与副作用 → 配置环境和凭证引用 → 联通与契约测试 → 隔离环境反例验证 → 发布版本 → 授权到具体项目和任务模板。连接成功不等于已授权执行全部操作。

| 接入类型 | 适合的能力 | 接入要求 |
| --- | --- | --- |
| 内置 SDK / 函数适配器 | Playwright、Midscene、断言、知识查询、数据工厂 | 显式注册函数与 schema；浏览器 page 由 worker 持有，模型只取得会话引用 |
| HTTP / OpenAPI | 业务只读查询、创建测试数据、环境健康检查 | 固定环境与端点；OpenAPI 生成候选配置后逐项确认写入含义、鉴权和字段 |
| MCP Server | 已有企业工具、浏览器或文件服务 | 记录协议/服务版本与工具清单，按工具授权，校验输入和结构化输出 |
| 受控脚本 / CLI | 历史测试脚本、专用诊断和数据处理 | 固定制品、入口和参数，锁定依赖；隔离进程或容器，限制网络、目录、资源和时长 |

MVP 实现 SDK/函数入口与一个业务 HTTP 适配器；v0.2 接入代表性 MCP 服务，并补齐 HTTP/OpenAPI 配置页。脚本运行器的完整自助能力可在隔离机制验收后开放。已有 CI 测试套件可通过受控任务触发和结果读取接入，不需全部改写为 MCP。

MCP 提供工具发现和调用协议，LangChain 有相应适配能力；它们不能替代本平台的授权、租约和副作用管理。协议规范版本和实际 SDK 版本实施时固定并验证，工具描述与只读/幂等提示不能直接作为可信权限依据。[MCP Tools 规范（2025-06-18）](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)、[LangChain MCP](https://docs.langchain.com/oss/javascript/langchain/mcp)

### 统一工具契约与会话管理

工具注册记录至少包含 tool_id、版本与制品哈希、输入/输出 schema、错误码、适用环境、副作用类别、幂等能力、超时与重试策略、并发方式、凭证引用、维护人和验证记录。HTTP GET 或 MCP 的只读标注不能独自决定操作无副作用。

每次调用由服务端补充 run_id、action_id、项目/租户、操作者、知识与 Skill 版本、对象范围、调用期限、预算和租约引用；模型不能覆盖这些字段。输出必须通过 schema 校验，包含执行状态、业务对象和证据引用。工具成功仅表示调用完成，业务 PASS/FAIL 由断言层给出。

建议规范化状态为 OK、VALIDATION_ERROR、POLICY_DENIED、DEPENDENCY_UNAVAILABLE、TIMEOUT、UNKNOWN_OUTCOME，并保留原始错误码。业务拒绝可以是一次成功的工具调用，随后由权限测试断言验证，不能简单把 HTTP 错误码等同于产品缺陷。

浏览器工具关联 worker、browser_session_id、角色及对象租约。同一页面串行操作，跨角色使用独立上下文；无状态查询可按预算并发。MCP 连接是否保持服务端会话取决于所选适配器与服务，不能假设每次调用天然共享浏览器；必须做连续调用和断线恢复验证。大文件、截图和 trace 返回受控引用及摘要，不把全部内容注入模型上下文。

写入动作只有在有可靠幂等或结果查询机制时才允许自动重试；超时后的状态记为未知副作用，先查询再决定恢复。取消应停止队列、在途执行与子进程，回收租约并登记清理结果。dry_run 只对已实现且经验证的工具开放；不能将真实写入包装为“模拟”。

### 实际权限与凭证

有效权限取任务授权、操作者权限、项目策略、Skill 允许依赖和工具本身限制的交集。委派、嵌套 Skill 及重试共享总预算，不能通过换入口扩大范围。明确授权的普通测试操作直接执行；越界或新增有影响的操作先按企业流程处理，再生成绑定新范围的任务版本。

任务执行身份默认只读正式知识和 Skill 制品，可写本次任务的工作目录与证据存储。框架自带文件写入、执行或其他工具也必须纳入相同限制，不能成为绕过注册工具入口的路径。具体后端和沙箱能力随锁定版本验证。[Deep Agents 定制能力](https://docs.langchain.com/oss/javascript/deepagents/customization)

凭证存入企业凭证服务，以引用绑定目标系统、环境与项目，在执行侧注入；不写入 SKILL.md、Wiki 或模型提示词。HTTP、MCP 与脚本执行器限制允许的目标和重定向；工具返回的文字是结果数据，不自动变成新指令。远程 MCP 与脚本包更新必须形成新版本，不能静默扩大工具清单、schema 或网络权限。

### 调试、发布、回滚与运行快照

Skill 生命周期：个人草稿 → 隔离调试 → 项目评审 → 已发布 → 废弃/禁用。工具生命周期：连接草稿 → 契约验证 → 隔离验证 → 项目可用 → 废弃/禁用。个人草稿在明确的调试任务中运行；正式 CI 和共享任务模板只能选择已发布版本。

任务启动时生成不可变运行清单，固定应用/测试代码、knowledge_release_id、Skill ID/版本/哈希、工具 schema/实现版本、模型/提示词、策略和数据工厂版本。缺依赖、同名冲突、循环依赖或版本不兼容时，在产生副作用前阻断，不静默换用“最新”。恢复时核对同一清单。

普通回滚只影响新任务的默认版本，在途任务继续使用已锁版本；若版本因权限或正确性问题被紧急禁用，应拒绝后续调用并安全结束相关任务，保留终止原因与清理状态。调试记录显示可复核的选择依据和调用结果，不需要保存模型内部思维过程。

| 验证对象 | 必需的代表性检查 | 发布底线 |
| --- | --- | --- |
| Skill 选择与输出 | 适用/不适用输入、必填项、输出 schema、缺失规则 | 不相关任务不误启用，缺关键依据不生成通过结论 |
| 工具契约 | 错误参数、错误对象、畸形返回、依赖不可用 | 错误可分类，未授权调用不发生业务写入 |
| 副作用与恢复 | 写入后超时、重复 action_id、取消、租约失效 | 反例中不重复写入；未知结果先查证，清理可追踪 |
| 版本与隔离 | 草稿混入、工具漂移、不同项目凭证、恢复版本不匹配 | 正式任务依赖固定，越权与错版本被明确拦截 |
| 测试判定 | 已知正确、已知缺陷、假成功提示和业务拒绝 | 关键缺陷样本不被判 PASS，原始失败不被“修复”掩盖 |

除确定性契约与隔离检查外，模型选择和输出应使用未参与调试的样例观察稳定性，记录样本量、误启用、阻断和费用。通过当前样例不代表已证明所有输入安全或测试完整。

### 首期交付与验收范围

MVP 第 1-6 周按 M11/M23-M25 交付 SDK/HTTP、Web 文本 Skill 编辑、隔离调试、管理员发布与版本回退。v0.2 的 S01/T01-T03 交付草稿辅助、HTTP/OpenAPI 配置、MCP、升级与紧急撤销；E03/E04 扩展受控脚本与跨项目共享。详细依赖与验收见《MVP开发任务清单与迭代路线》，不再沿用原八周统一排期。

MVP 可检查交付包括：2 个模板（审批权限、表单边界）、1 个由 QA 在 Web 自定义并完成评审的 Skill、SDK/HTTP 最小适配样例、版本清单、调试报告和回退记录；MCP 样例作为 v0.2 的独立验收。脚本接入先由测试开发使用受控制品；不将任意脚本自助上传计入首期验收。

验收关注测试人员能否使用已有工具独立完成 Skill 创建到调用、依赖是否可追溯、异常是否被正确处理、关键业务断言是否保持独立，以及从创建到可用的总工时。工具数量、Skill 数量和模型调用次数不作为收益指标。
